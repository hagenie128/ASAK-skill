# ASAK 프로젝트 공통 지침

## 대화 방식
- 모든 설명, 질문, 진행 상황, 결과 보고는 한국어로 작성한다.
- 초보자도 이해할 수 있는 쉬운 표현을 사용한다.
- 결론부터 말하고, 변경 이유와 확인 방법을 함께 설명한다.
- 사용자가 한 단어 명령을 입력하면 해당 스킬의 명시적 호출로 해석한다.
- 단순히 같은 단어가 문장에 포함됐다는 이유만으로 스킬을 자동 실행하지 않는다.

## 기술 기준
- Frontend: React + JavaScript
- Backend: Spring Boot + JPA
- React 컴포넌트: PascalCase
- JavaScript/Java 변수·함수: camelCase
- Database 테이블·컬럼: snake_case
- 기존 구조와 프로젝트 컨벤션을 먼저 확인한 뒤 따른다.

## 작업 모드
1. **검토 전용**: 파일을 수정하지 않고 문제와 근거만 보고한다.
2. **수정 포함**: 확인된 문제만 최소 범위로 수정하고 검증한다.
3. **설명·정리**: 코드를 바꾸지 않고 이해·발표·업무 정리에 맞는 결과 형식을 사용한다.

요청이 불명확하면 읽기와 분석부터 수행하며, 파괴적이거나 원격 상태를 바꾸는 작업은 실행하지 않는다.

## 공통 작업 원칙
1. 대상 범위와 관련 파일을 먼저 확인한다.
2. 호출 흐름과 현재 동작을 근거로 문제를 판단한다.
3. 추측만으로 수정하지 않고 재현, 로그, 테스트, 코드 흐름 중 가능한 근거를 확보한다.
4. 수정 요청이 있을 때만 가장 작은 범위로 수정한다.
5. 기존 UI, API 계약, 데이터 구조와 호환성을 우선 보존한다.
6. 빌드·테스트·린트·수동 재현 중 가능한 검증을 실행한다.
7. 실행하지 못한 검증은 이유와 미검증 범위를 명시한다.
8. 특정 파일명이 없으면 역할·함수명·호출 위치로 실제 구현을 찾고, 임의로 새 공통 파일을 만들지 않는다.

## 기본 결과 보고 형식
점검·수정 스킬은 다음 형식을 기본으로 사용한다.

1. 결론
2. 확인한 범위와 파일
3. 발견한 문제와 근거
4. 수정한 내용 또는 수정 제안
5. 검증 방법과 결과
6. 남은 위험과 미검증 항목
7. 공부 포인트

설명, 발표, 오늘, 이어서 스킬은 각 문서의 전용 결과 형식을 우선 사용한다.

## 승인 없이 실행하지 않는 작업
- commit, push, merge, rebase, branch 삭제
- 파일·폴더·브랜치·데이터 삭제
- DB DDL, migration 적용, 대량 데이터 수정
- 패키지 설치, 주요 버전 변경, lock 파일 대규모 변경
- 운영 환경 배포와 외부 서비스 설정 변경

## 절대 금지
- `git push --force`, `git reset --hard`, `git clean -fd`, 광범위 삭제 명령을 실행하지 않는다.
- 프로젝트 폴더 밖의 경로를 수정하지 않는다.
- 비밀키, 토큰, 개인정보를 출력·저장·커밋하지 않는다.
- `.env`, 인증서, 운영 비밀 설정을 임의 생성하거나 수정하지 않는다.
- 테스트를 통과시키기 위해 테스트를 삭제하거나 검증 강도를 낮추지 않는다.
- 검증하지 않은 결과를 완료라고 단정하지 않는다.
