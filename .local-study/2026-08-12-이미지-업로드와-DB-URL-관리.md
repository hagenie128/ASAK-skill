# 메뉴·옵션 이미지: 업로드, DB URL, 프런트 표시

## 문제

현재 Kiosk는 `public/assets`의 이미지 경로를 직접 사용한다. 옵션에서 SVG는 보이는데 PNG 사진은 보이지 않는다. 이후에는 Admin이 업로드한 이미지를 Backend가 HTTP 경로로 제공하고, DB에는 그 경로만 저장하고 싶다.

## 질문

- SVG는 보이는데 PNG는 왜 안 보이는가?
- 이미지 파일을 DB에 넣어야 하는가, URL만 넣어야 하는가?
- Admin 업로드부터 Kiosk 표시까지 데이터는 어떻게 흘러가야 하는가?

## 확인한 사실

### 현재 옵션 이미지가 보이지 않는 직접 원인

`ASAK-Kiosk/src/components/kiosk/OptionItem.jsx`는 아래처럼 **`iconUrl`만** 표시한다.

```jsx
{iconUrl ? <img className="option-item__image" src={iconUrl} alt="" /> : null}
```

따라서 `photoUrl`, `imageUrl`라는 이름으로 PNG 경로가 있어도 이 컴포넌트는 읽지 않는다.

또한 Backend `OptionItemResponse`와 `UserMenuMapper.xml`의 옵션 조회는 `iconUrl`/`imageUrl` 컬럼을 응답으로 넣지 않는다. 현재 옵션 응답에는 이름, 가격, 용량, kcal, 품절 같은 값만 있다. 즉 백엔드 연동 기준으로는 Kiosk까지 이미지 URL이 전달되지 않는다.

`public/assets/ingredients/catalog.json`에는 `iconUrl`(SVG)와 일부 `photoUrl`(PNG/JPG)이 함께 있지만, 이 파일은 현재 공개 정적 파일이다. Backend의 실제 옵션 API가 이 catalog JSON을 읽어서 내려 주는 구조는 아니다.

## 핵심 결론

- **파일 자체(BLOB)를 DB에 저장하지 않는다.** 작은 팀 프로젝트라도 파일은 서버 업로드 폴더 또는 클라우드 스토리지에 둔다.
- DB에는 파일의 저장 경로 또는 공개 URL만 저장한다.
- DB에 `http://localhost:8080/...` 전체 주소를 저장하지 않는다. 개발 PC 주소가 배포 환경에서 깨지기 때문이다.
- 권장 저장값은 상대 HTTP 경로다: `/uploads/options/uuid.png`

프런트는 API 서버 주소를 붙여 최종 주소를 만든다.

```text
DB:       /uploads/options/9d1...f2.png
개발:     http://localhost:8080/uploads/options/9d1...f2.png
배포:     https://api.example.com/uploads/options/9d1...f2.png
```

## 별도 서버·업로드 폴더가 아직 없을 때의 현실적인 선택

지금처럼 여러 PC에서 작업하고, 항상 켜져 있는 서버 컴퓨터나 공용 업로드 폴더가 없다면 `C:/ASAK-upload` 방식은 **아직 바로 쓰면 안 된다.**

왜냐하면 다음과 같기 때문이다.

```text
내 PC Backend가 C:/ASAK-upload/a.png를 제공
-> 내 PC에서는 http://localhost:8080/uploads/a.png 가 열림
-> 팀원 PC의 localhost:8080은 내 PC가 아니라 팀원 PC 자신
-> 팀원에게는 a.png가 없음
```

Backend가 실행되는 컴퓨터가 곧 파일 서버다. 물리적으로 별도 서버 컴퓨터가 아니어도, 한 PC에서 Backend를 켜고 다른 기기가 그 IP로 접근하게 만들면 그 PC가 임시 서버 역할을 한다.

### 지금 단계의 추천: Git으로 관리하는 public asset 유지

관리자가 즉석에서 업로드하는 기능은 잠시 미루고, 이미지 파일을 Kiosk의 `public/assets`에 넣어 Git으로 함께 관리한다.

```text
ASAK-Kiosk/public/assets/ingredients/photos/89.png
-> Kiosk 실행 서버가 GET /assets/ingredients/photos/89.png 로 제공
-> DB에는 /assets/ingredients/photos/89.png 저장 가능
-> 팀원도 Git pull 후 같은 파일을 가지므로 같은 이미지가 보임
```

이 방식은 현재 상황에서 가장 안정적이다. 단점은 새 이미지를 바꿀 때 Admin 화면에서 파일을 업로드하는 것이 아니라, 파일을 `public/assets`에 추가하고 Git 반영해야 한다는 점이다.

### 나중 단계: Backend PC를 임시 이미지 서버로 사용

시연할 때 한 대의 PC에서 Backend를 계속 실행할 수 있다면 그 PC의 폴더를 이미지 저장소로 쓸 수 있다.

```text
Backend 실행 PC: 192.168.0.10:8080
업로드 폴더:     C:/ASAK-upload
이미지 요청:      http://192.168.0.10:8080/uploads/options/a.png
```

이때 모든 Kiosk/Admin의 `VITE_API_BASE_URL`은 `http://192.168.0.10:8080`처럼 **같은 Backend PC 주소**를 가리켜야 한다. `localhost`를 쓰면 각 PC 자기 자신을 가리키므로 안 된다.

### 최종 단계: 공용 클라우드 저장소

여러 장소·여러 PC에서 이미지를 업로드하고 유지해야 할 때 Cloudinary, S3, Supabase Storage 같은 공용 저장소를 쓴다.

```text
Admin 업로드
-> 공용 스토리지에 파일 저장
-> DB에는 https://.../uuid.webp 저장
-> 어느 PC의 Kiosk/Backend에서도 같은 URL을 읽음
```

이 단계가 필요할 때만 계정·권한·비용·업로드 정책을 정한다. 지금 수업 프로젝트에서 먼저 도입할 필요는 없다.

### GitHub raw 링크는 가능한가?

가능하다. 공개 GitHub 저장소에 있는 고정 이미지라면 DB에 아래처럼 넣고 `<img src>`로 표시할 수 있다.

```text
https://raw.githubusercontent.com/<owner>/<repo>/<commit-sha>/public/assets/ingredients/photos/89.png
```

단, 브랜치명(`main`) 대신 **commit SHA**를 넣는 편이 좋다. `main`은 나중에 파일이 바뀌거나 삭제되면 과거 주문/메뉴가 같은 URL인데 다른 이미지를 보게 될 수 있다.

| 방식 | 컴퓨터를 계속 켜야 하나? | 지금 프로젝트에 적합한 경우 |
| --- | --- | --- |
| 내 PC Backend의 `/uploads/**` | 예. Backend와 그 PC가 켜져 있어야 함 | 한 PC로 짧게 시연할 때 |
| Kiosk `public/assets` + Git | 아니오. Kiosk를 실행/배포한 곳이 파일을 함께 제공 | 지금처럼 팀이 Git으로 고정 에셋을 관리할 때 |
| GitHub raw URL | 아니오 | 공개 저장소의 바뀌지 않는 소수 이미지, 빠른 시연 |
| GitHub Pages / Cloudinary / S3 | 아니오 | 여러 PC·배포 환경에서 계속 쓸 때 |

GitHub raw 링크의 한계:

- 저장소가 private이면 Kiosk 브라우저가 인증 없이 이미지를 못 가져올 수 있다.
- Admin 업로드 후 파일을 Git commit/push해야 하므로 "즉시 업로드" 기능이 아니다.
- 대량 이미지/운영 트래픽용 CDN·스토리지가 아니다.
- 파일 경로를 바꾸거나 커밋을 정리하면 DB URL이 깨질 수 있다.

따라서 지금은 **DB에 `/assets/...` 상대 경로를 저장하고 Kiosk public에 Git으로 파일을 함께 넣는 방법**이 가장 간단하다. 외부에서 같은 이미지를 직접 내려받아야 하는 요구가 생기면 GitHub raw보다 GitHub Pages 또는 이미지 스토리지를 검토한다.

## 수업 요구가 "이미지는 링크로 관리"일 때의 권장안

수업에서 말한 링크가 여러 PC에서 항상 열리는 이미지 주소를 뜻한다면, 최종 방향은 `public/assets`나 내 PC 폴더가 아니라 **클라우드 스토리지 URL을 DB에 저장**하는 것이다.

이 프로젝트에서는 Google Cloud Storage가 필수는 아니다. 메뉴·옵션 이미지 중심이라면 이미지 전용 스토리지인 **Cloudinary**를 먼저 쓰는 편이 설정이 적다. Supabase Storage도 가능하지만, 현재 MySQL/Spring Backend와 별개로 Supabase 프로젝트·버킷·정책을 새로 관리해야 한다.

```text
Admin에서 이미지 선택
-> Backend가 Cloudinary 업로드 API 호출
-> Cloudinary가 공개 HTTPS URL 반환
-> Backend가 그 URL을 DB에 저장
-> Kiosk GET 메뉴 상세 응답에 같은 URL 포함
-> <img src="https://res.cloudinary.com/..."> 표시
```

예시 DB 값:

```text
menu.image_url     = https://res.cloudinary.com/<cloud-name>/image/upload/v.../asak/menus/uuid.webp
opt_item.image_url = https://res.cloudinary.com/<cloud-name>/image/upload/v.../asak/options/uuid.webp
```

이 URL은 내 PC가 꺼져 있어도 Cloudinary가 제공하므로 Admin, Kiosk, Backend가 서로 다른 PC여도 같은 이미지를 본다.

### 절대 하면 안 되는 것

- Cloudinary API Secret을 Vite `.env`에 넣지 않는다. 프런트 빌드에 포함되어 노출된다.
- DB에 내 PC 경로(`C:\...`)나 `localhost` URL을 저장하지 않는다.
- 외부 업로드 성공 전에는 DB의 기존 이미지 URL을 바꾸지 않는다.

### 필요한 환경변수

Backend `.env`에만 둔다.

```env
CLOUDINARY_CLOUD_NAME=your_cloud_name
CLOUDINARY_API_KEY=your_api_key
CLOUDINARY_API_SECRET=your_api_secret
```

`.env.example`에는 변수 이름과 예시만 넣고 실제 값은 절대 올리지 않는다.

### 팀이 직접 구현할 순서

1. 팀 Cloudinary 계정을 만들고, 공동 계정 또는 팀이 접근 가능한 계정으로 프로젝트를 만든다.
2. Backend `.env`에 Cloudinary 키를 넣는다.
3. Admin 업로드 요청을 Backend가 받고, Backend만 Cloudinary에 업로드한다.
4. Cloudinary 응답의 `secure_url`을 사용한다. `url`보다 HTTPS인 `secure_url`이 안전하다.
5. 메뉴/옵션 저장 시 URL만 MySQL `image_url`에 저장한다.
6. Kiosk 옵션 DTO/Mapper가 `imageUrl`을 반환하고 `OptionItem`이 그 값을 렌더링한다.
7. Admin/Kiosk/다른 PC 브라우저에서 같은 URL을 새 탭으로 열어 확인한다.

### Cloudinary가 아닌 Google Cloud Storage를 택할 때

Google Cloud Storage도 구조는 같다: Bucket에 업로드 -> 공개 또는 서명 URL 획득 -> DB에 URL 저장. 다만 버킷, IAM 권한, 서비스 계정, CORS, 과금 프로젝트를 먼저 설정해야 한다. 팀이 Google Cloud를 이미 쓰거나 그 설정 자체를 학습해야 할 때 선택한다.

### 구현 완료 기준

- [ ] DB에 `https://...` 이미지 URL이 저장된다.
- [ ] 내 PC Backend를 끈 뒤에도 새 탭에서 URL이 열린다.
- [ ] 다른 팀원 PC의 Kiosk에서도 같은 이미지가 표시된다.
- [ ] 실제 Secret은 Backend `.env`에만 있고 Git에 없다.

## Cloudinary 문서 두 개: ASAK에서 실제로 쓰는 부분

### 문서 역할 구분

| 문서 | ASAK에서 쓰는 때 | 핵심 |
| --- | --- | --- |
| Image Upload API | Admin이 메뉴/옵션 이미지를 저장할 때 | 파일을 Cloudinary에 올리고 HTTPS URL과 public ID를 받는다. |
| Transformation Reference | Kiosk가 같은 원본을 화면 크기에 맞게 보여 줄 때 | URL 또는 React SDK로 크롭·크기·자동 WebP/AVIF 품질을 적용한다. |

둘을 섞지 않는다. **업로드는 한 번**, 화면 변환은 메뉴 카드/상세/옵션 카드에서 필요할 때마다 전달 URL에만 적용한다. 원본 파일을 여러 크기로 DB에 중복 저장하지 않는다.

### 1. DB에는 무엇을 저장할까?

링크만 요구되어도 아래 두 값을 같이 저장하는 편이 좋다.

```text
image_url       : Cloudinary의 secure_url (바로 img src에 쓸 HTTPS 링크)
image_public_id : Cloudinary 파일 식별자 (교체, 삭제, 변환 URL 생성에 사용)
```

예시:

```text
image_url       = https://res.cloudinary.com/szztwoeh/image/upload/v123/asak/menus/3f4a.webp
image_public_id = asak/menus/3f4a
```

`secure_url`만 저장하면 기본 표시는 가능하다. 하지만 나중에 이전 파일을 삭제하거나 React `url-gen`으로 변환 URL을 만들 때 `public_id`가 필요하므로 같이 두는 것을 추천한다.

```sql
ALTER TABLE menu
  ADD COLUMN image_public_id VARCHAR(255) NULL AFTER image_url;

ALTER TABLE opt_item
  ADD COLUMN image_url VARCHAR(500) NULL AFTER icon_url,
  ADD COLUMN image_public_id VARCHAR(255) NULL AFTER image_url;
```

이 migration은 아직 실행하지 않았다. 실제 스키마를 다시 확인한 뒤 팀이 적용한다.

### 2. 업로드: Admin -> Spring Backend -> Cloudinary

권장 방식은 **signed upload를 Backend가 수행**하는 것이다.

```text
Admin: 파일만 multipart/form-data로 Backend에 전달
Backend: API Secret으로 서명 또는 Java SDK 업로드
Cloudinary: secure_url, public_id 응답
Backend: 필요한 두 값만 Admin에 응답
Admin: 메뉴/옵션 저장 API에 imageUrl, imagePublicId 전달
DB: URL과 public ID 저장
```

Admin이 호출할 내부 API 예시:

```http
POST /api/admin/media/images
Content-Type: multipart/form-data

file: 선택한 PNG/JPG/WebP
target: MENU | OPTION
```

Backend가 돌려줄 응답 예시:

```json
{
  "imageUrl": "https://res.cloudinary.com/szztwoeh/image/upload/v123/asak/options/3f4a.webp",
  "imagePublicId": "asak/options/3f4a"
}
```

Cloudinary Upload API의 `public_id`는 파일의 전달·접근 식별자다. 이미지의 경우 확장자는 넣지 않고, 원본 파일명 대신 Backend가 UUID를 만들어 `asak/menus/<uuid>` 또는 `asak/options/<uuid>` 형식으로 준다. Cloudinary는 같은 public ID의 덮어쓰기와 CDN 캐시 문제를 안내하므로, ASAK에서는 기존 파일을 덮어쓰기보다 **새 UUID를 발급하고 DB URL을 교체**하는 편이 안전하다. [Cloudinary Upload API reference](https://cloudinary.com/documentation/image_upload_api_reference)

Backend `.env`에만 둘 값:

```env
CLOUDINARY_CLOUD_NAME=szztwoeh
CLOUDINARY_API_KEY=your_api_key
CLOUDINARY_API_SECRET=your_api_secret
```

`CLOUDINARY_API_SECRET`은 React/Vite 환경변수에 넣지 않는다. `VITE_`로 시작하는 값은 브라우저 번들에 포함될 수 있다.

### 3. React에서 직접 업로드하는 unsigned 방식은 언제 쓰나?

Cloudinary는 브라우저가 `upload_preset`과 파일을 보내는 unsigned upload도 지원한다. 이 방식은 API Secret을 노출하지 않는 대신, 공개 preset을 악용해 제3자가 파일을 올릴 수 있는 위험을 preset 정책으로 줄여야 한다.

```text
학원 프로젝트의 관리자 업로드
-> Backend 경유 signed upload 권장

개인 포트폴리오의 빠른 이미지 선택 데모
-> unsigned preset도 가능
```

현재 ASAK에는 관리자 인증도 완성되지 않았으므로, unsigned upload를 먼저 열지 않는다.

### 4. Transformation: 화면마다 원본을 다르게 전달하기

Cloudinary의 transformation은 원본을 새로 저장하는 기능이 아니라, URL에 규칙을 넣어 CDN이 필요한 크기·형식으로 전달하게 하는 기능이다.

ASAK에서 처음 쓸 값은 아래 네 개면 충분하다.

| 값 | 의미 | ASAK 사용처 |
| --- | --- | --- |
| `width`, `height` | 전달할 크기 | 메뉴 카드, 옵션 64px 이미지 |
| `crop: fill` | 지정된 카드 크기를 꽉 채우도록 자르기 | 메뉴 카드/옵션 카드 |
| `gravity: auto` | 자동으로 중요한 위치 중심 크롭 | 음식 사진 |
| `format: auto`, `quality: auto` | 브라우저에 맞는 형식과 품질 자동 전달 | 모든 공개 이미지 |

메뉴 카드: `320 x 240`, 옵션 카드: `64 x 64`, 메뉴 상세: `800 x 600`처럼 화면마다 목적을 정한다. 모든 화면에 500 x 500 자동 크롭을 똑같이 쓰면 음식 사진이 잘릴 수 있다.

### 5. React SDK를 쓸 때

사용자가 받은 예제의 `Cloudinary`, `AdvancedImage`, `auto()`는 **Kiosk 표시용**이다. 업로드 코드는 아니다.

`cloudName`은 공개되어도 되는 식별자지만, API Secret은 넣지 않는다.

```jsx
import { Cloudinary } from "@cloudinary/url-gen";
import { AdvancedImage } from "@cloudinary/react";
import { fill } from "@cloudinary/url-gen/actions/resize";
import { autoGravity } from "@cloudinary/url-gen/qualifiers/gravity";

const cld = new Cloudinary({
  cloud: { cloudName: import.meta.env.VITE_CLOUDINARY_CLOUD_NAME },
});

export function MenuImage({ publicId, alt }) {
  const image = cld
    .image(publicId)
    .format("auto")
    .quality("auto")
    .resize(fill().width(320).height(240).gravity(autoGravity()));

  return <AdvancedImage cldImg={image} alt={alt} />;
}
```

이 컴포넌트는 `imagePublicId`가 있어야 쓸 수 있다. 처음에는 DB의 `imageUrl`을 기존 `<img>`에 그대로 넣고, 크기 최적화가 실제로 필요해질 때 SDK를 붙여도 된다.

### 6. ASAK API 계약

메뉴 상세 GET에서 메뉴/옵션 모두 이름을 통일한다.

```json
{
  "imageUrl": "https://res.cloudinary.com/...",
  "imagePublicId": "asak/options/3f4a"
}
```

현재 `OptionItem.jsx`는 `iconUrl`만 읽는다. Cloudinary 사진을 붙일 때는 `imageUrl`을 우선하고 기존 SVG는 대체값으로 둔다.

```jsx
const mediaUrl = item.imageUrl ?? item.iconUrl;
```

이렇게 하면 사진이 등록된 옵션은 Cloudinary PNG/JPG/WebP를 보이고, 사진이 없는 기존 옵션은 SVG 아이콘을 계속 보인다.

### 7. 실제 구현 순서

1. Cloudinary Media Library에 음식 사진 하나를 직접 업로드해 `secure_url`과 `public_id`를 확인한다.
2. DB 컬럼과 Backend DTO/Mapper의 `imageUrl`, `imagePublicId` 계약을 확정한다.
3. Kiosk에서 먼저 `imageUrl ?? iconUrl` 표시를 연결하고, DB에 수동으로 넣은 한 URL이 뜨는지 확인한다.
4. 그 다음 Admin -> Backend -> Cloudinary 업로드 API를 만든다.
5. 이미지 교체 시 새 URL 저장, 이전 public ID 삭제 순서를 구현한다.
6. 마지막에 카드별 크기 최적화(Transformation)를 붙인다.

### 8. 이 순서를 쓰는 이유

이미지가 "표시되는 것"과 "업로드되는 것"을 한 번에 만들면 오류 원인을 구분하기 어렵다. 먼저 DB URL -> Backend 응답 -> Kiosk img 표시를 확인하면, Cloudinary 업로드 API는 나중에 독립적으로 붙일 수 있다.

## 1시간 안에 이미지·아이콘 링크로 정리하는 가장 빠른 방법

목표는 **관리자 업로드 기능 구현이 아니라**, Cloudinary 링크를 DB -> API -> Kiosk 화면까지 한 번 보이게 만드는 것이다.

### 하지 않을 것

- Spring Cloudinary SDK 설치
- Admin 업로드 버튼 구현
- API Secret을 프런트에 넣기
- 이미지 테이블을 새로 만들기
- URL 자동 변환/삭제 기능

이것들은 이번 한 시간 범위를 넘는다.

### 0~10분: Cloudinary에 직접 올리기

1. Cloudinary Console -> Media Library를 연다.
2. 메뉴 사진은 PNG/JPG/WebP, 아이콘은 SVG를 그대로 끌어다 놓아 업로드한다.
3. 폴더는 보기 좋게만 `asak/menus`, `asak/options`, `asak/icons`으로 나눈다. 폴더 구조가 기능에 필수는 아니다.
4. 각 파일에서 **`secure_url` (https 링크)** 을 복사한다.
5. 아래처럼 간단한 표에 기록한다.

| 대상 | DB ID | 종류 | secure_url |
| --- | ---: | --- | --- |
| 닭가슴살 추가 | 105 | 옵션 사진 | `https://res.cloudinary.com/...` |
| 닭가슴살 아이콘 | 105 | SVG 아이콘 | `https://res.cloudinary.com/...` |

`api_secret`은 이 과정에서 사용하지 않는다.

### 10~25분: DB에 URL 넣기

현재 스키마 기준으로 메뉴는 `menu.image_url` 컬럼이 있다. 메뉴 사진부터 먼저 바꾼다.

```sql
-- 먼저 현재 값 확인
SELECT id, name, image_url
FROM menu
WHERE id IN (201, 202);

-- 한 건만 먼저 바꿔 화면 확인
UPDATE menu
SET image_url = 'https://res.cloudinary.com/<cloud-name>/image/upload/.../menu.webp'
WHERE id = 201;
```

옵션은 현재 `opt_item.icon_url`이 있으므로, **이번 한 시간에는 아이콘 URL을 여기에 저장**한다.

```sql
SELECT id, name, icon_url
FROM opt_item
WHERE id = 105;

UPDATE opt_item
SET icon_url = 'https://res.cloudinary.com/<cloud-name>/image/upload/.../icon.svg'
WHERE id = 105;
```

주의: 옵션 사진 PNG와 옵션 아이콘 SVG를 둘 다 쓸 별도 `image_url` 컬럼은 아직 없다. 빨리 확인할 때는 `icon_url`에 **SVG 하나만** 넣는다. PNG 사진까지 보이게 하려면 아래 "25~45분"의 최소 코드/DB 변경이 필요하다.

### 25~45분: 옵션 SVG 아이콘을 Kiosk API로 전달하기

현재 Kiosk `OptionItem.jsx`는 `iconUrl`을 이미 표시한다. 문제는 Backend 옵션 조회가 `oi.icon_url AS iconUrl`을 응답하지 않는다는 점이다.

팀원이 직접 바꿀 최소 범위:

1. `ASAK-back/.../OptionItemResponse.java`에 `private String iconUrl;` 추가
2. `ASAK-back/.../UserMenuMapper.xml` 옵션 SELECT에 아래 한 줄 추가

```sql
oi.icon_url AS iconUrl,
```

3. 서버 재시작
4. Kiosk 메뉴 상세 GET 응답에서 `optionGroups[].items[].iconUrl`이 HTTPS Cloudinary URL인지 확인
5. 이미 있는 `OptionItem.jsx`의 `<img src={iconUrl}>`가 SVG를 표시하는지 확인

### PNG 사진도 오늘 같이 보이게 하려면 (45~60분)

옵션에 PNG 사진을 보이게 하려면 컬럼 하나와 필드 두 개가 추가로 필요하다.

```sql
ALTER TABLE opt_item ADD COLUMN image_url VARCHAR(500) NULL AFTER icon_url;
UPDATE opt_item
SET image_url = 'https://res.cloudinary.com/<cloud-name>/image/upload/.../option.png'
WHERE id = 105;
```

그리고 다음만 추가한다.

```text
OptionItemResponse.java : String imageUrl
UserMenuMapper.xml      : oi.image_url AS imageUrl
OptionItem.jsx          : const mediaUrl = item.imageUrl ?? item.iconUrl
                          <img src={mediaUrl} ...>
```

이렇게 하면 PNG 사진이 있으면 PNG를, 없으면 기존 SVG 링크를 보인다.

### 마지막 5분: 확인 순서

1. Cloudinary `secure_url`을 브라우저 새 탭에서 열어 이미지가 보이는지 확인한다.
2. DB SELECT로 URL이 들어갔는지 확인한다.
3. Kiosk 메뉴 상세 API 응답에 같은 URL이 있는지 확인한다.
4. Kiosk 화면에서 이미지가 보이는지 확인한다.
5. 다른 PC 또는 휴대폰에서도 Cloudinary URL을 열어 본다.

### 오늘의 완료 기준

- [ ] 메뉴 사진 한 장이 DB의 Cloudinary HTTPS 링크로 표시됨
- [ ] 옵션 SVG 아이콘 한 개가 DB의 Cloudinary HTTPS 링크로 표시됨
- [ ] 가능하면 옵션 PNG 한 개도 `image_url`로 표시됨
- [ ] Cloudinary API Secret은 어디에도 코드/DB/Git에 넣지 않음

한 시간이 지나면 그다음 작업은 Admin 업로드 버튼과 Backend signed upload API다. 오늘은 **직접 업로드 -> URL DB 저장 -> Kiosk 표시**까지만 완료해도 충분하다.

## 지금 이미지 경로를 어떻게 맞출지

현재 `public/assets` 방식에서는 Backend가 전체 `http://localhost...` 주소를 만들 필요가 없다. DB에는 Kiosk 정적 경로만 넣는다.

```text
opt_item.image_url = /assets/ingredients/photos/89.png
```

Kiosk에서는 이 값을 그대로 `img src`에 쓸 수 있다. `/assets/...`는 현재 Kiosk가 떠 있는 같은 주소로 요청된다.

다만 Backend API가 `imageUrl: "/assets/..."`를 내려 주고, Kiosk가 다른 호스트에 배포되는 경우에도 Kiosk가 해당 assets를 제공하는 구조여야 한다. 즉 이 경로는 **Backend 이미지 경로가 아니라 Kiosk 빌드에 포함된 정적 파일 경로**다.

## 지금 할 일과 나중에 할 일 분리

| 시점 | 할 일 | 파일 위치 | DB 값 |
| --- | --- | --- | --- |
| 지금 | PNG를 Git 관리 public asset에 추가 | `ASAK-Kiosk/public/assets/...` | `/assets/...png` |
| 지금 | 옵션 API가 사진 경로를 응답하도록 계약 맞춤 | Backend DTO/Mapper | `imageUrl` |
| 나중 | Admin에서 파일 선택·업로드 | Backend 실행 PC의 업로드 폴더 | `/uploads/...` |
| 더 나중 | 여러 장소에서 영구 업로드 | 공용 클라우드 저장소 | `https://...` |

즉 **지금은 `public/assets`도 HTTP로 제공된다.** Vite가 개발 중 `/assets/...` 경로를 응답하고, 빌드 후에도 해당 파일이 Kiosk 정적 파일로 포함된다. 차이는 Admin이 런타임에 바꿀 수 있느냐와, 모든 PC가 같은 파일을 보장하느냐이다.

## 추천 데이터 모델

### 1단계: 지금 프로젝트에 가장 단순한 방식

기존 메뉴는 `menu.image_url`을 계속 사용한다.

옵션 사진을 쓰려면 `opt_item`에 의미가 분명한 컬럼을 추가한다.

```sql
ALTER TABLE opt_item
  ADD COLUMN image_url VARCHAR(500) NULL AFTER icon_url;
```

의미를 나눈다.

| 컬럼 | 용도 | 예시 |
| --- | --- | --- |
| `icon_url` | 작은 SVG 아이콘 | `/uploads/options/icons/chicken.svg` |
| `image_url` | 옵션 카드의 PNG/JPG/WebP 사진 | `/uploads/options/images/chicken-uuid.webp` |
| `menu.image_url` | 메뉴 대표 사진 | `/uploads/menus/caesar-uuid.webp` |

옵션에 사진이 하나만 필요하면 `icon_url`에 PNG를 넣어도 기술적으로는 보인다. 하지만 아이콘과 사진의 의미가 섞이므로, 앞으로 둘 다 쓸 가능성이 있으면 `image_url`을 따로 두는 편이 낫다.

### 2단계: 이미지가 늘어날 때의 공용 테이블

메뉴·옵션·재료·배너 이미지 관리가 많아질 때만 도입한다.

```text
media_asset
- id
- storage_key          : uploads/options/uuid.webp
- original_filename    : chicken.png
- content_type         : image/webp
- size_bytes
- width / height       : 선택
- created_at
- deleted_at           : 선택
```

그리고 `menu.image_asset_id`, `opt_item.image_asset_id`처럼 FK를 둔다.

지금은 메뉴와 옵션 이미지 두 종류뿐이므로 **1단계 URL 컬럼 방식으로 시작**하고, 억지로 공용 미디어 테이블을 먼저 만들지 않는다.

## 전체 데이터 흐름

```text
Admin에서 PNG 선택
-> POST /api/admin/uploads/images (multipart/form-data)
-> Backend가 파일 형식·용량 검사
-> 서버 업로드 폴더에 UUID 파일명으로 저장
-> { "path": "/uploads/options/images/uuid.webp" } 응답
-> Admin이 메뉴/옵션 저장 요청의 imageUrl에 path를 포함
-> DB menu.image_url 또는 opt_item.image_url 저장
-> Kiosk 메뉴 상세 GET 응답에 imageUrl 포함
-> Kiosk가 API base URL + imageUrl로 <img src> 표시
```

## 직접 구현 순서

### A. 업로드 파일을 어디에 저장할지 정하기

개발 환경에서는 Backend 프로젝트 바깥의 업로드 폴더를 쓴다.

```text
C:\ASAK-upload\menus\
C:\ASAK-upload\options\
```

`src/main/resources/static`에 업로드 파일을 넣지 않는다. 빌드 결과물에 섞이고 서버 재시작/배포 때 사라질 수 있다.

`.env`에 경로를 둔다.

```env
UPLOAD_DIR=C:/ASAK-upload
```

`.env.example`에는 실제 개인 경로 대신 예시만 남긴다.

```env
UPLOAD_DIR=C:/path/to/asak-upload
```

### B. Backend 정적 파일 제공

Spring 설정에서 URL과 실제 폴더를 연결한다.

```text
HTTP 요청: /uploads/**
실제 폴더: file:${UPLOAD_DIR}/
```

예: DB의 `/uploads/options/images/a1.webp` 요청은 `${UPLOAD_DIR}/options/images/a1.webp` 파일을 읽는다.

이 부분은 Controller가 아니라 정적 리소스 설정으로 처리해도 된다. 단, 나중에 관리자만 볼 수 있는 비공개 이미지는 같은 공개 경로를 쓰면 안 된다.

### C. 업로드 API 계약

```http
POST /api/admin/uploads/images
Content-Type: multipart/form-data

file: 선택한 이미지 파일
target: MENU | OPTION
```

성공 응답 예시:

```json
{
  "path": "/uploads/options/images/5cf6b7d8.webp",
  "contentType": "image/webp",
  "sizeBytes": 182340
}
```

실패 응답은 기존 API 오류 형식에 맞춰 구분한다.

| 실패 | 예시 코드 | 화면 안내 |
| --- | --- | --- |
| 파일 없음 | `IMAGE_FILE_REQUIRED` | 이미지를 선택해 주세요. |
| 허용하지 않는 형식 | `IMAGE_TYPE_NOT_ALLOWED` | PNG, JPG, WebP만 올릴 수 있어요. |
| 파일 너무 큼 | `IMAGE_FILE_TOO_LARGE` | 5MB 이하 파일만 올릴 수 있어요. |
| 저장 실패 | `IMAGE_UPLOAD_FAILED` | 업로드에 실패했어요. 다시 시도해 주세요. |

검증 기준:

- 확장자만 믿지 말고 `contentType`과 실제 파일 헤더도 확인한다.
- 허용 형식: PNG, JPEG, WebP
- 최대 용량: 팀에서 정하되 예시는 5MB
- 서버 저장 이름은 사용자 파일명이 아닌 UUID로 만든다.
- 원본 파일명은 화면 표시가 필요할 때만 별도 메타데이터로 보관한다.

### D. 메뉴/옵션 저장 API에 URL 넣기

업로드 API 성공 뒤 받은 `path`를 form state에 넣고, 기존 메뉴 저장 요청에 보낸다.

```json
{
  "name": "닭가슴살 시저 샐러드",
  "imageUrl": "/uploads/menus/5cf6b7d8.webp"
}
```

옵션을 저장하는 API가 생기면 같은 방식으로 `imageUrl`을 보낸다.

```json
{
  "optionItemId": 105,
  "name": "닭가슴살 추가",
  "imageUrl": "/uploads/options/images/8a1d.png"
}
```

### E. Kiosk 조회 응답과 렌더링

Backend 옵션 DTO에 `imageUrl` 필드를 추가하고, `UserMenuMapper.xml`의 옵션 SELECT에 `oi.image_url AS imageUrl`을 넣는다.

Kiosk의 `OptionItem.jsx`는 사진 우선, 아이콘 대체 순서로 받는다.

```jsx
const mediaUrl = item.imageUrl ?? item.iconUrl;

{mediaUrl ? <img className="option-item__image" src={mediaUrl} alt="" /> : null}
```

주의: Backend가 상대 경로만 준다면 Kiosk의 API base URL을 붙이는 헬퍼가 필요하다.

```js
function resolveMediaUrl(path) {
  if (!path) return null;
  if (path.startsWith("http://") || path.startsWith("https://")) return path;
  return `${import.meta.env.VITE_API_BASE_URL}${path}`;
}
```

이 헬퍼를 메뉴 카드, 메뉴 상세, 장바구니, 옵션 카드에서 공통으로 사용한다. 화면마다 `localhost:8080`을 직접 적지 않는다.

## PNG가 지금 안 보이는지 확인하는 순서

1. 브라우저 Network에서 메뉴 상세 GET 응답의 `optionGroups[].items[]`에 `imageUrl` 또는 `photoUrl`이 있는지 본다.
2. 없다면 Backend DTO/Mapper가 보내지 않는 문제다.
3. 값은 있는데 화면에 안 보이면 `OptionItem.jsx`가 그 필드명을 실제로 읽는지 본다. 현재는 `iconUrl`만 읽는다.
4. 최종 `<img src>` 주소를 새 탭에서 열어 200과 실제 이미지 `Content-Type`이 오는지 본다.
5. 404면 DB 경로와 서버 업로드 폴더의 상대 경로가 다른 것이다.
6. 200인데 깨지면 이미지 파일 손상, 잘못된 MIME, CORS/보안 헤더를 확인한다.

## 파일 삭제와 교체 규칙

이미지를 교체했다고 이전 파일을 바로 지우지 않는다.

```text
새 파일 업로드 성공
-> DB URL 갱신 성공
-> 이전 경로가 어떤 메뉴/옵션에서도 참조되지 않는지 확인
-> 그 뒤 이전 파일 삭제 또는 삭제 예정 표시
```

DB 갱신 실패 시에는 새로 업로드된 파일이 고아 파일이 된다. 처음에는 운영자가 주기적으로 정리해도 되고, 나중에는 업로드 트랜잭션/정리 배치를 둔다.
