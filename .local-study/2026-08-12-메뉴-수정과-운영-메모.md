# 메뉴 수정과 운영 기능 메모

## 문제

- 메뉴 수정 후 상세 화면에 새 데이터가 보이는가?
- 핵심 재료와 옵션 단백질은 왜 제거 규칙이 다른가?
- 변경사항 건수와 영양 재계산은 어떻게 생각해야 하는가?
- 주문 완료 카드는 왜 화면에서 남을 수 있는가?

## 질문

- 메뉴 수정 화면의 데이터는 언제 다시 조회해야 하는가?
- 변경사항은 무엇을 한 건으로 세는가?
- TTS와 RTOS 연결은 주문 상태 갱신을 막지 않게 어떻게 분리하는가?

## 확인한 사실

- 메뉴 목록 새로고침 신호 `tick`은 목록을 다시 불러오는 용도다. 선택된 메뉴 상세도 새로 받으려면 상세 조회의 의존성에 그 신호가 반영되어야 한다.
- 레시피에 들어가는 단백질 재료는 `core`가 되며 제거할 수 없다. 고객이 옵션으로 선택한 단백질은 기본 재료와 다른 주문 옵션 데이터이므로 제거 가능 규칙과 분리한다.
- 변경 건수는 기본 정보의 변경 필드 수, 재료/옵션 그룹/태그의 추가·삭제·내용 변경 행 수를 기준으로 셀 수 있다.
- 현재 영양 재계산은 화면용 계산 방향만 정리되어 있고, 서버 영양 계산 API는 별도 구현이 필요하다.
- Live Order는 완료 상태 변경 뒤 목록을 다시 조회해야 완료 카드가 사라진다. TTS를 `await`하면 TTS가 끝날 때까지 목록 갱신이 막힐 수 있다.

## 방법

### 옵션 그룹에서 필수를 먼저 보이게 하기

```js
const sortedOptionGroups = [...optionGroups].sort((a, b) => {
  if (Boolean(a.isRequired) === Boolean(b.isRequired)) return 0;
  return a.isRequired ? -1 : 1;
});
```

- 렌더링할 때만 `sortedOptionGroups.map(...)`을 쓴다.
- 저장 payload는 원래 `optionGroups`를 유지하면 표시 순서만 바뀐다.

### 영양 재계산의 기본식

```text
재료별 kcal = 재료 kcal × (메뉴 사용량 quantity / 영양 기준량 servingG)
메뉴 총 kcal = 모든 재료별 kcal의 합
```

- `quantity`와 `servingG`의 단위가 둘 다 g일 때만 이 식을 바로 쓸 수 있다.
- ml, 개 단위는 단위 변환 기준을 별도로 정해야 한다.
- 실제 서비스 정본은 프런트 계산값보다 서버 계산 결과가 되어야 한다.

### Live Order 완료와 TTS 순서

```text
상태 변경 PATCH 성공
-> Live 목록 refresh
-> 완료 카드 제거
-> TTS는 기다리지 않고 재생
```

TTS 실패는 안내만 하고 주문 완료 상태를 되돌리지 않는다.

### RTOS 연결 원칙

```text
DB에서 PREPARING -> COMPLETED 성공
-> Backend가 RTOS 클라이언트에 주문번호 전달
-> RTOS 실패는 로그/안내로 처리
```

- 브라우저가 RTOS에 직접 연결하지 않는다.
- RTOS 전송 실패 때문에 DB 주문 완료를 되돌리지 않는다.
- 상태 전이 검증으로 같은 주문의 중복 출력도 막는다.

## 응용

- 목록·상세가 동시에 있는 다른 화면도 목록 새로고침과 상세 새로고침을 분리해서 확인한다.
- 변경 건수는 저장 직전 상태와 최초 로드 상태를 비교하는 방식으로 다른 편집 화면에도 적용할 수 있다.
- 외부 기능(TTS, RTOS, 알림)은 핵심 DB 처리 이후에 실행해 화면 갱신과 상태 저장을 막지 않게 한다.

## 주의할 점

- 메뉴 수정 성공 응답만으로 DB 반영과 상세 화면 반영이 모두 확인된 것은 아니다.
- core 재료와 고객 옵션은 데이터 경로가 다르므로 같은 제거 규칙을 무조건 적용하지 않는다.
- TTS/RTOS 실제 동작은 브라우저 Network와 수신 클라이언트 로그로 따로 확인해야 한다.
