# 재료 영양정보: 정규화와 고객 화면 조회

## 문제

고객 화면은 재료의 전체 영양성분이 아니라 칼로리와 단백질만 필요하다. 그래서 `ing` 테이블에 `kcal`, `protein_g`를 추가했는데, 기존 `ing_nutr`에도 같은 값이 있어 중복이 생겼다.

## 질문

- 고객 화면이 두 값만 쓴다는 이유로 `ing`에 복사해도 되는가?
- 조인 때문에 고객 메뉴 조회가 무거워지지는 않는가?

## 확인한 사실

- 실제 DB `ing_nutr`에는 `UNIQUE (ing_id)`가 있다. 재료 하나당 영양행은 최대 하나이므로 `ing -> ing_nutr`는 1:1 관계다.
- 실제 DB에는 `ing.kcal`, `ing.protein_g`와 `ing_nutr.kcal`, `ing_nutr.protein_g`가 함께 있고, 확인한 표본에서는 값도 같다.
- 현재 `UserMenuMapper.xml` 옵션 조회는 이미 `ing_nutr`를 조인해 `kcal`을 가져온다.
- 고객 메뉴의 대표 영양정보는 `menu_nutr`를 사용한다. 재료 영양정보와 메뉴 영양정보는 다른 목적이다.

## 권장 구조

**정본은 `ing_nutr` 하나로 둔다.**

```text
ing
  = 재료의 정체성: id, 이름, 분류, 품절 여부

ing_nutr
  = 재료의 영양정보: 기준 제공량, kcal, 단백질, 탄수화물, 지방 등

menu_nutr
  = 메뉴 조합 결과 영양정보
```

고객 화면에서 칼로리/단백질만 필요하면 전체 영양정보를 전송하지 말고 SQL SELECT에서 필요한 두 컬럼만 고른다.

```sql
SELECT
  i.id,
  i.name,
  n.kcal,
  n.protein_g AS proteinG
FROM ing i
LEFT JOIN ing_nutr n ON n.ing_id = i.id
WHERE i.id = ?;
```

이것은 영양 행이 1:1이고 `ing_nutr.ing_id`가 유니크이므로, "테이블이 많아서 무거운 조인"으로 볼 수준이 아니다. 필요한 컬럼만 받아 DTO에 넣으면 된다.

## 지금 추가한 `ing.kcal`, `ing.protein_g`는 어떻게 할까?

### 가장 권장: 중복 컬럼을 제거한다

고객 조회 매퍼를 `ing_nutr` 조인 방식으로 통일한 뒤, 데이터 백업/검증 후 `ing.kcal`, `ing.protein_g`를 제거한다.

장점: 수정할 때 한 곳만 바꾸면 되고 값 불일치가 없다.

제거 전 확인 SQL:

```sql
SELECT i.id, i.name,
       i.kcal AS ing_kcal, n.kcal AS nutr_kcal,
       i.protein_g AS ing_protein_g, n.protein_g AS nutr_protein_g
FROM ing i
LEFT JOIN ing_nutr n ON n.ing_id = i.id
WHERE NOT (i.kcal <=> n.kcal)
   OR NOT (i.protein_g <=> n.protein_g);
```

결과가 0건이고, 코드가 `ing.kcal`, `ing.protein_g`를 읽지 않는 것을 확인한 뒤에만 제거한다.

```sql
ALTER TABLE ing
  DROP COLUMN kcal,
  DROP COLUMN protein_g;
```

이 SQL은 아직 실행하지 않는다. 실제 적용 전에는 migration 파일과 영향받는 매퍼를 팀에서 확인한다.

### 차선: 읽기 최적화용 복제값으로 명시한다

정말 측정 결과 조인이 병목이라면 `ing.kcal`, `ing.protein_g`를 읽기 전용 요약값으로 유지할 수 있다. 이것은 정규화된 데이터가 아니라 **비정규화 캐시**다.

이 경우 반드시 정한다.

```text
정본: ing_nutr
복제본: ing.kcal, ing.protein_g
갱신 책임: 재료 영양 수정 Service 한 곳
갱신 방식: 한 트랜잭션에서 ing_nutr와 ing를 함께 UPDATE
```

Admin, seed SQL, 배치가 각자 두 테이블을 따로 업데이트하면 값이 다시 어긋난다. DB Trigger로 자동 동기화할 수도 있지만, 수업 프로젝트에서는 숨은 동작이 늘어나므로 Service 한 곳에서 명시적으로 처리하는 편이 이해하기 쉽다.

## 고객 API를 가볍게 만드는 방법

고객 화면별 응답을 다르게 만든다.

| 화면 | 필요한 영양값 | 추천 데이터 원천 |
| --- | --- | --- |
| 메뉴 목록 | 메뉴 kcal 정도 | `menu_nutr.kcal` |
| 메뉴 상세 | 메뉴 kcal/단백질 등 | `menu_nutr` |
| 옵션 카드 | 옵션 kcal/단백질 | `opt_item -> ing_nutr` 필요한 두 컬럼만 |
| 재료 빼기 목록 | 보통 영양값 불필요 | `ing`만 조회 |

"고객 화면이 전체 영양정보를 안 쓴다"는 이유는 **응답 DTO를 작게 만들 근거**이지, 영양값을 `ing`에 복사할 근거는 아니다.

## 방법

1. `ing_nutr`을 재료 영양의 정본으로 확정한다.
2. 고객 옵션 DTO에 정말 필요한 `kcal`, `proteinG`만 둔다.
3. `UserMenuMapper.xml`에서 `ing_nutr` 1:1 조인으로 두 값만 SELECT한다.
4. `ing`의 중복 컬럼을 유지할지 제거할지 팀에서 결정한다.
5. 유지한다면 영양 수정 Service 한 곳에서 두 값 동기화 규칙을 만든다.
6. `EXPLAIN ANALYZE`에서 실제 병목이 나타난 경우에만 비정규화를 검토한다.

## 주의할 점

- 메뉴 영양(`menu_nutr`)과 재료 영양(`ing_nutr`)은 합치지 않는다. 메뉴는 여러 재료의 조합 결과다.
- 재료 사용량과 기준 제공량이 다르면 kcal/단백질은 비율 계산이 필요하다.
- `LEFT JOIN`을 쓰면 영양정보가 아직 없는 재료도 고객 화면에서 사라지지 않고, 값만 null로 내려갈 수 있다.
- 지금은 `ing_nutr.ing_id` 유니크 인덱스가 있으므로 이 1:1 조인을 위해 인덱스를 더 추가할 필요가 없다.
