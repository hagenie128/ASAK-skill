# 매출 화면과 데이터 분석

## 문제

매출은 주문·결제·주문항목을 조합해 만들어서, 데이터가 늘면 조회가 무거워질 수 있다.

## 질문

- 지금 화면에는 무엇이 있고, 실제 DB로 바꾸려면 무엇이 필요한가?
- TOP 메뉴 말고 실무적인 분석은 무엇을 보여 줄 수 있는가?
- 인덱스나 집계 테이블은 언제 필요한가?

## 확인한 사실

- 화면은 매출 요약(SCR-019), 월별(SCR-020), 일별(SCR-021) 세 개다.
- 현재 `useSalesQuery.js`는 mock을 사용한다. 백엔드 통계 Controller/Service/Mapper는 TODO 뼈대다.
- 실제 DB에는 일별/시간별 매출 및 TOP 메뉴 뷰 네 개가 존재한다.
- 실제 `payment` 테이블에는 `paid_at` 인덱스가 없다. 인덱스 추가 여부는 실제 매출 SQL의 `EXPLAIN ANALYZE` 후 결정한다.

## 방법

1. 결제 승인 기준의 순매출·환불액·주문 수·객단가 정의를 먼저 정한다.
2. 매출 요약 API 하나를 먼저 연결한다.
3. KPI, 일별 표, 시간대 차트의 순매출 합계가 같은지 확인한다.
4. 월별과 일별 화면을 연결한다.
5. 느린 쿼리가 실제로 확인되면 기간 조건과 실행계획을 보고 인덱스를 검토한다.

## 응용

- 현재 DB만으로 카테고리 매출 비중, 옵션 부착률, 재료 제외율, 주문 조합, 취소·환불률을 분석할 수 있다.
- 품절 손실은 품절 이력과 장바구니 검증 실패 로그가 생긴 뒤 분석한다.
- 전환율은 메뉴보기·장바구니·결제시작 이벤트가, 이익률은 재료 원가 이력이 필요하다.

## 주의할 점

- 매출은 주문 완료 시각이 아니라 결제 승인 시각 기준이다.
- MySQL 뷰는 저장된 결과가 아닐 수 있으므로, 뷰가 있다고 빠르다고 단정하지 않는다.
- 오래된 SQL 덤프는 현재 DB의 인덱스 근거로 쓰지 않는다.
